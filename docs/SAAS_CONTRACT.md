# SaaS usage and billing example contract

This is a fictional synthetic example. It demonstrates the platform pattern on a second domain and does not model a real billing system.

| Feed | Grain and key | Revision | Measures and rules |
| --- | --- | --- | --- |
| `usage` | One metered event, keyed by `event_id` | Numeric `revision` is a full event image; latest revision wins | Integer `units` for one `customer_id` and `period`; aggregate before joining an invoice. |
| `invoices` | One invoice, keyed by `invoice_id` | Numeric `revision` is a full invoice image | Integer `billed_units`, decimal `unit_price`, and `currency` for one customer and period. |

Both feeds carry `source_updated_at` as an ISO UTC timestamp. Raw Delta retains source file name, file content hash, and row payload hash. A byte-identical renamed retry is suppressed as the same source evidence; a corrected usage or invoice record has a higher revision and remains in raw history. Equal key and latest revision with different payload fails the run before publication and is recorded in the run ledger. A later valid higher revision resolves an older conflict without deleting raw evidence. The current revision of each event and invoice contributes once.

CSV files need the required columns above; additional columns are retained in raw evidence. Files with missing required columns and rows with the wrong field count are listed in `input_quarantine`. Rows with missing keys, invalid revisions, periods, units, prices, currencies, or UTC source timestamps are also quarantined. Valid rows in the same batch continue. Quarantine entries include a reason and source file; typed invalid rows include their payload hash. A later valid revision can supersede an invalid one. A feed containing only invalid rows has no current business rows, and source freshness still reports the arrived files.

Reconciliation has one row per customer and billing period. It sums billed units across distinct current invoice IDs before joining observed usage, preventing usage fan-out. It reports `invoice_count`, sorted `invoice_ids`, and `billed_amount`. Exact duplicate envelopes are suppressed. If invoice IDs share a price and currency, `expected_amount` is observed units multiplied by that price. Multiple prices or currencies yield `MULTIPLE_UNIT_PRICES` or `MIXED_CURRENCY` and leave the ambiguous expected amount null. Mixed currencies also leave `currency` and `billed_amount` null rather than summing unlike money. Otherwise the comparison reports `BILLED_USAGE_MISMATCH`, `MISSING_USAGE`, or `MISSING_INVOICE` when applicable. No payment action is taken.

## Local backfill and repair

`edp saas-run --root <root>` rebuilds the full current reconciliation from retained inputs. `edp saas-run --root <root> --start-period YYYY-MM --end-period YYYY-MM` requires a published baseline, recomputes the inclusive period range from all retained inputs, and copies untouched periods from the prior generation. A new complete generation is staged and then published. Repeating the same range with the same source evidence produces the same business rows while retaining prior generations. The per-root `evidence/run_ledger.jsonl` records each success, injected failure, or raised error with run ID, range, prior generation, and published or staged generation. After a failed run, use `--repair-run-id <id>` with its original range; repair rejects a successful run ID or a changed range. `edp repair-pending --domain saas --root <root>` selects the newest unresolved failure and its range. Repair creates a new run and links it to the failed run. Local commands hold a per-root process lock; the bounded hosted SaaS acceptance uses an isolated root. A separate hourly hosted SaaS job repaired a seeded failed period through a periodic trigger; see [schedule evidence](../evidence/databricks-repair-schedules.json).

The walkthrough starts with 200 observed and 190 billed units. A revision changes one event from 80 to 70 units. An injected failure occurs after a new reconciliation Delta product is staged but before the pointer changes. Readers retain the preceding generation; rerunning publishes the 190-unit result.
